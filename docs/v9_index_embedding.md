# Index v9: fine-tuned text embedder and `semantic_v3` text

From v9 on (`genizah_merged_v9` and its bibliography index), indices built from this repo use a different model **and** a different document text than v8. The vectors are not comparable with v8 ones: documents and queries must come from the same model, and both indices switch together.

**Model.** `isaacmg/genizah-embed-qwen3-0.6b` pinned at revision `dbfab73f1e91a6b95eba728541cc5a391a88d933` (`FINETUNED_MODEL_NAME` / `FINETUNED_MODEL_REVISION` in `src/embeddings/qwen_text_embedding.py`, the `QwenTextEmbedding` default; the base `Qwen/Qwen3-Embedding-0.6B` constants stay for checking old indices). 1024-d, last-token pooling, L2-normalised, cosine, fp32, `max_seq_length = 8192` set on load. The Hub repo is private, so the loader reads `HF1_TOKEN` (else `HF_TOKEN`) from the environment. Documents are embedded raw. Queries always get `QUERY_PROMPT` (`Instruct: Given a search query, retrieve relevant passages\nQuery: `) passed explicitly, never `prompt_name="query"`: the prompt saved with the model is the stock web-search one.

**Text.** `create_text_representation(doc, version)` in `src/embeddings/text_representation.py` is the one text function for indexing, verification and training. `v8` is today's `doc.create_text_representation()` text, unchanged. `semantic_v3` (the default) is what the model was trained on: `src/embeddings/semantic_text.py`, a port of genizah_search `evals/embedding_audit/semantic_text.py` with identical regexes (pinned by tests). It drops the `Document ID:` / `Shelf Mark:` lines, editor credits and empty field lines, and masks the record's own shelf mark, cited shelf marks and PGPIDs as `[shelfmark]`. Bibliography pages lose only their `Source PDF:` line; `Shelf marks mentioned:` and inline marks stay.

**Eligibility.** A fragment gets no vector (`semantic_eligible: false`) when its semantic text is empty, under 40 characters, or only a boilerplate label (frozen list `src/embeddings/data/boilerplate_descriptions_v3.json`, 64 labels) plus `Language` / `Document Type` / `Date` lines: 13,419 of the 74,687 records in the 2026-10-06 merged file. These records are still indexed for shelf-mark and BM25 lookup, and an empty string is never embedded. A bibliography page is ineligible only when nothing but its PDF line is left. Every document carries `semantic_eligible` and `text_representation_version`.

**`_meta` contract.** `model_name`, `model_revision` (sha), `query_prompt`, `text_representation_version`, `max_seq_length`, and three canaries:

- `canary`: a fixed string in document mode. Together with the pre-v9 `embedding_model` / `embedding_model_revision` keys, this is what the site's startup gate reads.
- `query_canary`: the same string in query mode.
- `document_canary`: the first eligible record's `doc_id`, text and vector.

**Writer guard.** An indexer refuses to add to an existing index whose `_meta` differs on `model_name`, `model_revision` or `text_representation_version`. Pre-v9 indices always differ. The destination index names are code-level constants — `DEFAULT_INDEX_NAME` (`genizah_merged_v9`) in `index_merged_genizah.py` and `DEFAULT_BIBLIOGRAPHY_INDEX` (`bibliography_text_only_0.8`) in `index_all_bibliography.py` — bumped in the code for each new build; `--index` overrides them, and `genizah_merged_v6`–`v8` are refused unless `--i-know-this-is-live` is passed.

**Build and verify** (Elasticsearch credentials and `HF1_TOKEN` in the environment):

```bash
python -m src.datasets.indexing.index_merged_genizah                      # DEFAULT_INDEX_NAME; --limit 200 for a smoke run
python -m src.datasets.indexing.bibliography.index_all_bibliography      # DEFAULT_BIBLIOGRAPHY_INDEX; --dry-run lists books
python -m src.datasets.indexing.verify_reembedded_indexes                # defaults follow the two constants
```

The verifier:

- checks the `_meta` contract against the local embedder;
- reproduces all three canaries, rebuilding the document canary's text with the local text function;
- checks that exactly the eligible documents have vectors;
- re-embeds random documents from `create_text_representation(doc, version=_meta["text_representation_version"])`.

## Catalogue enrichment updater (2026-10-09)

**What changed in the document model.** `GenizahDocument.from_merged_format` now also lifts KTIV scholarly identifications into `alt_titles`, after the "Varying form of title" values: every scholarly entry's `frame` (the identified passage, e.g. `[Talmud Yerushalmi]: Sanhedrin 10:2 – 3`) and its work `title` unless that title is generic (`KTIV_GENERIC_WORK_TITLES`). Alternate titles that differ only in brackets, quote marks, spacing or case are kept once (`_alt_title_key`), so a varying title and the frame restating it count as one. A new field `subjects` (`SUBJECTS_MAPPING`: multilingual text with a `keyword` sub-field) holds what a record is about: the KTIV `full_catalog.subjects`, the generic work titles ("Talmud Bavli", "Mishneh Torah": the frozen-eval re-score showed queries that name a work lose ground when its name leaves the text) and the PGP tags, minus collection-wide labels, numeric authority ids, PGP workflow tags and anything naming the legacy catalogue store. A second new field `genres` (`GENRES_MAPPING`, the same shape) holds the genre taxonomy: every level of the KTIV scholarly `domain` paths, cleaned the same way, minus any level that is already one of the record's subjects. All three fields feed `full_text_content`; the embedding text gains a `Subjects:` line after `Alternate titles:`, but `genres` never reaches it. A few hundred taxonomy terms cover the whole corpus, and in the 2026-10-09 frozen-eval re-score, embedding them pulled distinctive records towards their genre's centroid, so `genres` serves facets and BM25 only. `semantic_text.content_lines` never counts a `Subjects:` line as content, so the frozen `semantic_v3` eligibility of texts without that line is unchanged and the `_meta` text version stays `semantic_v3`. The 40-character floor is measured on the text without its `Subjects:` lines (`semantic_text.eligibility_text`), so keywords never lift a short label over it either: a record becomes newly eligible only through a scholarly identification in `Alternate titles:`.

**Updating an existing index in place.** An index built before this change (`genizah_merged_v9`) lacks `subjects`, `genres` and the new alternate titles, and its vectors were embedded from the old text. `src/datasets/indexing/update_catalogue_enrichment.py` brings it in line with the current merged file and document model without a rebuild, under the index's existing `_meta` contract (same embedder, revision and text version). Run the dry run first; the real run is a separate decision:

```bash
python -m src.datasets.indexing.update_catalogue_enrichment --dry-run --report enrichment_dry_run.json   # reads only
python -m src.datasets.indexing.update_catalogue_enrichment --i-know-this-is-live                       # writes; LIVE_INDEX_NAME (the served index)
```

It streams the merged file in chunks of 200 records and reads each document's indexed `description`, `alt_titles`, `subjects`, `genres`, `semantic_eligible`, `description_source`, `text_representation_version` and `embedded_text_sha256` with `mget`. The text counts as changed when the stored `embedded_text_sha256` differs from the hash of `embedding_text(doc, version).text`. For a document without the hash (every document an indexer wrote, so all of v9 before the first run), it counts as changed when `description`, `alt_titles`, `subjects` or `genres` differs; `genres` is included there although it is never embedded. With the hash, a `genres`-only change leaves the text alone and is a field update. Per document:

- `unchanged`: the four catalogue fields and the text match; nothing is written.
- `update/reembed`: the text changed and is eligible. Writes `description`, `alt_titles`, `subjects`, `genres`, `full_text_content`, `embedding_vector` (the embedding of that text), `semantic_eligible: true`, `text_representation_version`, `embedded_text_sha256` and `catalogue_fields_updated_at`. A re-embed of a document the index held without a vector is an *eligibility flip*, the headline count.
- `update/fields_only`: a catalogue field changed but the text is not eligible (or, with a stored hash, did not change). Writes the four catalogue fields, `full_text_content`, `catalogue_fields_updated_at` and `embedded_text_sha256` (the hash of the current text, so the stored hash never goes stale on a document that stays without a vector), no vector.
- `generated`: the vector comes from a machine-generated description (`description_source: generated_from_consensus`) and a catalogue field changed. Writes the four catalogue fields, `full_text_content` and `catalogue_fields_updated_at`, never the vector or the eligibility flags.
- `refused:would_lose_vector`: the changed text is not eligible but the document holds a vector. Nothing is written (this should not happen: enrichment only adds text).
- `missing`: the record is not in the index. Documents are never created.

Guards, all before the merged file is streamed, are those of `update_generated_descriptions`: the live names are refused without `--i-know-this-is-live`; the index must exist and its `_meta` must match the embedder and the text version (`IndexMetaMismatchError`); a real run also checks that the loaded embedder is the one the guard checked and that it reproduces the `_meta` string canary (cosine > 0.99), and checks every vector's size against `_meta.dims` before writing it. Missing mapping fields (`alt_titles`, `subjects`, `genres`, `embedded_text_sha256` as `keyword`, `catalogue_fields_updated_at` as `date`) are added with `put_mapping` (properties only) before the first write; `_meta` is written only by `--refresh-document-canary` (below). A dry run loads no model and writes nothing.

The summary, printed and written as JSON with `--report`, gives the scanned / missing / generated / unchanged / `update/reembed` / `update/fields_only` / refused counts, the flips, which catalogue fields drove the updates, the unchanged documents whose indexed eligibility disagrees with the current rule (expected 0), the documents stamped with another text version, the missing mapping fields, up to five example ids per category, and whether the `_meta` document canary's text changed. A real run adds the documents written and the canary cosine. Progress is logged every 2,000 records together with a safe `--skip` value.

The run is idempotent: everything it wrote is `unchanged` on the next run, so an interrupted run can simply be started again or resumed with `--skip N`. A document holding a generated-description vector keeps it even when its enriched catalogue text has become eligible, while `update_generated_descriptions` refuses documents that hold a catalogue vector; running this updater first lets the catalogue text win wherever it is now eligible.

**Verifier.** The self-consistency check needs no change: it re-embeds `create_text_representation(doc, version)` of the same merged file, which is exactly the text this updater embeds. Every re-embed writes the vector together with `semantic_eligible: true`, so the eligibility-vs-vectors check stays consistent. The document-canary check compares `_meta.document_canary.text` with the record's current text, which the model change broke (the first eligible record gained subjects): `--refresh-document-canary` re-embeds that same record's current text after the writes and stores it in `_meta.document_canary`, the updater's only `_meta` write (every other key is kept; refused when the record is gone or no longer eligible). Dry run of 2026-10-09 with the final rules (`subjects` / `genres` split, generic work titles as subjects, alternate-title de-duplication): 78,113 scanned, 49,793 `unchanged`, 27,231 `update/reembed`, 1,089 `update/fields_only`, 261 eligibility flips, 0 missing / refused; the changes come from `subjects` on 21,379 records, `genres` on 13,808 and `alt_titles` on 6,251 (a document can count under several), no description changed since the v9 build; 5,813 of the re-embeds differ only in `genres` and reproduce their vectors, the price of stamping every touched document with `embedded_text_sha256` on this first run.
